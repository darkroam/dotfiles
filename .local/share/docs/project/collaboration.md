# 协作规约（用户 × dsh × codex）

> 建立于 2026-08-31 · v0.1 · 由用户确认生效（2026-08-31）
> 本文综合 clear-jlpt-n2、cni249、innogpu-fh2m-debian-trixie 三个参考项目的协作经验，按本仓库约束适配，
> 是三角色协作的唯一权威规约；其他文档只链接本文，不复制规则。

## 一、角色分工

| 角色 | 职责 |
|------|------|
| 用户（最终决策者） | 提出需求；对关键问题与重大决策（改名/删档/范围取舍/规约变更/批准提交）最终拍板；负责协作档案的本机保存与备份 |
| dsh（监督者） | 把需求整理成自包含提示词与验收标准；**主动完善需求：在用户要求范围之外主动提出优化建议与补充要求，与用户沟通确认**；审查 codex 成果、给出裁决与问题清单；维护轮次档案与 INDEX 状态；经批准后提交并推送仓库变更 |
| codex（实现者） | 按提示词落实实现、交付可验证成果；**发挥主观能动性：不局限于提示词与用户要求范围，主动发现问题（含范围外问题）、多提建议与更优方案**；授权分级内可自主解决并汇报，范围外登记上报 |

## 二、标准流程（每轮迭代）

1. 用户向 dsh 提出要求 → dsh 创建轮次目录 `.local/share/collab/R{编号}-{YYYY-MM-DD}-{主题}/`，同时写入：
   `要求.md`（用户要求原文 + 完整提示词）、`汇报.md`（模板先行，状态占位「待开发」），并在
   `INDEX.md` 登记该轮（状态「待开发」）。
2. dsh 将要求整理成完整提示词（§三规范；自包含，codex 无需追问即可执行）；整理过程中可主动提出
   优化建议与补充要求，与用户沟通确认后写入（§四）。
3. 用户将提示词交给 codex 执行；codex 如有更优方案可主动提出，经确认后执行（§四）。
4. codex 完成后填写 `汇报.md`（执行摘要/做了什么/验证结果/偏差及原因/自主发现与处理/遗留问题），
   并将当前轮次标为「待审查」。该状态只表示交付完成，不代表审查通过。
5. dsh 审查（§六标准）→ 不通过：问题清单写入 `汇报.md`、状态「返工」→ 用户转交 codex 修改 →
   回到第 4 步；通过：审查结论写入 `汇报.md`、`INDEX.md` 状态「通过」→ 仓库变更按 §七 提交。
6. 重大决策由用户拍板，dsh 记录进轮次档案。

状态流转：待开发 → 开发中 → 待审查 → 通过 / 返工。状态更新责任人为 dsh；codex 仅可在完成
交付时把当前轮次推进为「待审查」，dsh 负责审查后的「通过/返工」以及 INDEX 的最终状态维护。

## 三、提示词规范（dsh 产出）

- **自包含**：写明背景、目标、具体任务、验收标准、边界、授权范围。
- **三层边界**（每条提示词按此分级写入，不得违反）：
  - **绝对禁止**（任何情况下不可修改）：仓库本体 `$HOME/.cfg/`；未跟踪的私密目录（`.ssh/`、
    `.gnupg/`、`.password-store/` 等，本就不入库）；用户急救备份 `.config-backup.bak`；历史存档
    与已完结审计原文（`audits/`、`planning/history.md`）。
  - **默认保护**（默认不可修改，仅当提示词明确批准精确路径范围后才可改）：影响实机生效的核心
    配置——`.config/x11/`、`.config/shell/`、安装系统（`.local/bin/dotcfg`、`.local/lib/dotfiles/`）、
    平台档案 `.local/share/docs/platforms/`、`~/.gitignore`。
  - **自由范围**：其余跟踪文件，但须遵守 §六 门禁与本仓库既有规范（维护策略、文档质量规范、
    平台事实规则）。
- **明确交付物**：文件路径、格式、登记要求（新文档须同步 `.local/share/docs/README.md` 索引与
  根 `README.md` 导航）。
- **验收标准给足**：可逐条核对；涉及测试/一致性检查的基线以当时实际运行为准，不把快照数字
  固化进规约。
- **不限制实现路径**：鼓励 codex 主动提出更优方案。
- 涉及实机生效或外部系统的轮次必须写明**授权窗口**与**停止条件**（超时/硬件异常/批量失败 →
  停止上报，不擅自续时或扩大操作）。

## 四、主动性（dsh 与 codex）

### dsh 主动性

- 完善需求不以用户要求范围为上限：发现要求中的缺口、风险、更优路径时，主动提出优化建议与
  补充要求，与用户沟通确认后再写入提示词或直接完善方案；不擅自替用户拍板。
- 审查中发现超出提示词范围的改进机会，同样主动提出建议交用户决策。

### codex 主动性（权限与义务）

- 收到提示词后，若认为有更优方案（工具选型、分批策略、产出结构等），可主动提出替代方案并
  说明理由，经确认后执行。
- **不局限于提示词与用户要求范围**：开发过程中主动发现问题（含范围外、用户未提及的问题），
  多提建议，不闷头硬干。
- 执行中发现提示词有误、需求与实际冲突、素材缺失，主动汇报。
- **自主修复分级**：
  - 授权范围内、低风险、完成任务必需的问题 → 可直接修复，并在汇报中说明（修了什么、为什么）；
  - 范围外、影响实机环境、高风险或改变接口/契约的问题 → 只登记与上报，取得授权后再处理。
- 遇阻塞或重大偏差，及时汇报进展与影响面；按停止条件停止并上报，不擅自扩大操作。
- 汇报必须包含：做了什么、产出文件清单、验证结果（实测数据）、与提示词的偏差及原因、自主发现
  与处理、遗留问题/需决策事项。

## 五、协作档案（`.local/share/collab/`）

- 位置：`.local/share/collab/`（与 `.local/share/docs/` 同级；唯一外层目录，所有轮次子目录收于
  其下，根目录不散放）。
- **本机私有目录**：本仓库是公开项目（GitHub `darkroam/dotfiles`），协作档案必须本机私有——由
  `~/.gitignore` 排除（`.local/share/collab/`），不提交、不推送、不上传 GitHub、不参与任何公开
  分发；任何轮次不得解除该排除或将本目录内容加入暂存区；本机保存与备份由用户负责，dsh 与
  codex 不得将本目录内容外传。
- 结构：`R{编号}-{YYYY-MM-DD}-{主题}/`，创建轮次时即含 `要求.md`（用户要求原文 + dsh 提示词）
  与 `汇报.md`（模板先行），可选附加交付物；**轮次目录内只允许 Markdown 文件**（禁止二进制、
  代码快照等）。
- 模板：`templates/要求.md`、`templates/汇报.md`（每轮从模板创建，避免格式漂移）。
- 索引：`INDEX.md` 记录每轮 轮次/日期/主题/状态；与轮次目录按编号双向一一对应；状态集合为
  待开发/开发中/待审查/通过/返工。
- 隐私纪律：本目录虽不入库，仍不得记录凭据、私钥、token、密码原文；并遵循平台事实规则——
  不得记录主机名、用户名、序列号、UUID、MAC/IP、账户、原始 EDID；需要时只保留占位符与受控
  证据位置。任何内容若要离开本机（贴出、转交），必须先脱敏。
- 跨设备协作：本目录不跨设备同步；与 codex 分处不同设备时，由用户转交提示词与汇报内容，
  dsh 在本机归档。
- 机械校验工具为 `.local/lib/project-tools/validate-collab`，是项目内部工具，不进入用户 PATH；
  调用形式为 `validate-collab [COLLAB_DIR]`，省略参数时检查 `$HOME/.local/share/collab/`。
- 工具检查：INDEX 表头、分隔行、数据行与状态白名单；合法日历日期；轮次编号唯一；INDEX 与目录的
  编号、日期、主题双向精确对应；根目录、模板和轮次文件集合；必需的 `要求.md`/`汇报.md`；以及
  整棵树内的符号链接、嵌套目录、散落文件、非 Markdown 文件和隐藏文件。
- 隐私检查覆盖全部普通 Markdown 文件（含 INDEX 与隐藏 Markdown），大小写无关地识别具体凭据赋值、
  常见密钥/令牌形态、私网 IPv4、MAC、UUID、`/home/<user>` 路径，并以运行时 `hostname` 和
  `id -un` 做精确身份词元检查。政策文字中单独出现 `token`、`password` 等字段名不视为泄漏；只有
  具体赋值或已知凭据形态才命中，以避免本规约自身产生误报。诊断只输出文件与行号，不回显敏感值。
- 退出码：`0` 表示通过且无输出（目录不存在同样通过），`1` 表示发现违规并逐行写入标准错误，`2`
  表示用法错误。持久 fixture 位于 `.local/share/test/collab/validate-collab.bats`。

## 六、审查标准（本仓库特化）

- [ ] 验收标准逐条核对通过。
- [ ] 无越界改动：§三 绝对禁止项零改动；默认保护项仅在授权精确范围内改动。
- [ ] 影响实机生效的配置改动有验证与回滚路径说明；shell/脚本改动通过语法检查（`bash -n`/
      ShellCheck）与相关测试。
- [ ] 文档变更符合[文档质量规范](docs-standard.md)；提交前完成全库一致性检查（术语统一、内部
      链接有效、文档关系成立、无平台泄漏）。
- [ ] 涉及安装系统的改动通过 Bats 测试（`.local/share/test/installation/`；基线以当时实际运行
      为准）。
- [ ] 平台事实只写 `platforms/` 档案，通用文档不复制平台事实。
- [ ] 隐私合规：本次提交与协作档案无凭据/主机名/用户名等敏感信息原文。
- [ ] git status 干净、commit 信息清晰、无遗漏文件、无无关改动混入。

## 七、git 与提交

- 仓库是 bare 仓库（`$HOME/.cfg`、work-tree `$HOME`），命令
  `c='/usr/bin/git --git-dir=$HOME/.cfg/ --work-tree=$HOME'`；远端 `git@github.com:darkroam/dotfiles.git`。
- **默认停在提交前**：dsh 与 codex 均不得未经授权自行 commit/push；审查通过并经用户批准后，
  由 dsh 提交并推送，提交说明由 dsh 定稿。
- codex 如需自行提交，须在本轮提示词中明确授权。
- 仅提交本轮相关文件（`c add <路径>` 显式路径），不得混入无关改动；本机未跟踪的私有文件
  一律不得 add。
- 审查通过前不推送；推送前检查：`c status` 干净、`c log` 最近提交、`c fetch` 确认远端状态、
  无 ahead/behind 遗留。
- 禁止 force push；重写已发布历史（如历史邮箱元数据清理）必须用户单独批准，不在常规轮次执行。

## 八、定期文档梳理（回头看）

- **触发**：每完成 5–6 个协作轮次，或发生重大结构/角色/流程变化，或大量新内容落地后，由 dsh
  发起；用户可随时提前发起。
- **目的**：消解文档与实现的不一致、内部冲突与矛盾；把新机制融入常青文档；优化文档结构与导航；
  确认需求完整、方向明确。
- **执行（两阶段，先盘点后修改）**：
  1. 盘点（只读）：codex 产出双向对照表——实现→文档（新机制/工具/脚本是否有权威文档描述）与
     文档→实现（每条现状断言是否与实现一致）；列出结构问题与疑似冲突；标出需用户决策的重大项。
  2. 修改（经确认）：dsh 审查盘点、用户对决策项拍板后 codex 才动笔；每处修改记录
     「事实依据 → 文档修改」一行，重大结构调整单独说明理由。
- **纪律**：只改「当前描述」，不改写历史记录（历史基线、审计、旧决策、已完成 TODO 保持原样，
  必要时追加新条目）；同一事实保持单一权威来源，其他文档只链接不复制；机械门禁全程保持通过；
  未决决策项写入轮次 `汇报.md`，不擅自定案。

## 九、与本仓库既有规范的关系（边界）

- 本文只治理协作流程；仓库的技术与文档规范继续遵循[维护策略](maintenance-policy.md)、
  [文档质量规范](docs-standard.md)、平台事实规则与安装测试体系。
- 涉及实机生效的改动，除本轮提示词授权外，仍须遵守维护策略的工作流（提出方案 → 用户确认 →
  执行 → review → 用户确认）。
- 同一事实保持单一权威来源：本文是协作流程的唯一权威，其他文档只链接、不复制规则。
